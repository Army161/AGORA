Vision

Teams are already running several agents. Nothing sits underneath them.

As soon as a team runs more than one AI agent, it needs somewhere for those agents to coordinate — shared work, explicit ownership, and a record of what happened. Today that place does not exist, so the human becomes the message bus. Agora is that missing substrate: one workspace where claude.ai web, Cowork, Claude Code, the Chrome extension and Claude Design see the same tasks, take leases on work, lock what they touch, and hand off with an audit trail.

The problem

Agents today are single-player. Each surface has its own context window and no memory of what another agent just did — so the same work gets done twice, overwritten, or lost somewhere between two chat windows.

Every surface is an island

Context lives inside one conversation. An agent in a browser tab cannot see what an agent in the terminal decided sixty seconds ago, because there is nothing outside either conversation that holds the decision.

Duplicated and clobbered work

Two agents pick up the same task because neither can tell the other it was taken. Two agents edit the same file because there is no notion of ownership. The last writer wins, silently.

The human is the integration layer

Coordination happens by copy-paste. The real project state lives in the operator's head and in scrollback, which means it cannot be queried, resumed after a crash, or audited afterwards.

None of this is a capability gap in the models. Each agent, individually, does the work well. The failure is between them.

The insight

Coordination is a state problem, not a model problem. A stronger model does not stop two agents from writing to the same file at the same time — it just does it more confidently.

Humans solved this problem a long time ago, and not with intelligence. We solved it with boards, tickets, check-outs, locks and handover documents: cheap, external, shared state that anyone can read to find out who owns what. Those primitives work because they are outside the participants.

Agents need the same primitives, but with machine-native semantics. Human coordination assumes a person will eventually notice that a ticket is stale, that someone left for the day, that a claim was never released. Agents do not notice; they crash, get closed mid-task, or quietly stop. So the primitives have to be self-correcting.

Human practiceMachine-native equivalentIn Agora
A board showing who is doing what A shared task list where each task has at most one owner at a time agora_board, agora_add_task
"I've got this" in standup A lease with a TTL, so a claim expires without anyone having to notice agora_claim_task, agora_release_task
Checking out a file before editing An explicit resource lock with a holder and an expiry agora_lock_resource, agora_unlock_resource
Meeting notes and "as discussed" An append-only log with a monotonic sequence number, so an agent asks only what changed since it last looked agora_events(since_seq)
A handover doc when someone goes on leave A structured handoff that must be acknowledged and then completed agora_create_handoff, agora_ack_handoff

Why this is the durable layer

The coordination layer is orthogonal to the model question. It sits below the models and above the surfaces, and it does not care which one is currently best: a task with an owner and a lease is still a task with an owner and a lease when the model behind the agent changes next quarter. Model capability is where the competition is; shared state is where the continuity is.

That is also why it should be boring and inspectable. The engine is plain files and plain Python — the state is readable by a human with a text editor, versionable in git, and replaceable underneath without changing the contract the agents see.

What genuinely runs

  • A working MCP server. 19 tools, every one namespaced agora_*, covering presence, tasks with leases, resource locks, handoffs, updates, direct messages, shared memory and the event log.
  • A coordination engine with no dependencies. server/store.py is pure Python standard library, which is what makes it portable, auditable and trivial to test anywhere.
  • A concurrency model that is tested, not asserted. Cross-process mutex via atomic directory creation; atomic JSON writes (temp file plus os.replace); an append-only event log with a monotonic sequence number; TTL leases on tasks and locks so a crashed agent can never permanently block work. One of the 52 tests puts 8 threads in competition for a single task claim and asserts that exactly 1 wins.
  • Cross-platform CI. The suite runs on Ubuntu, macOS and Windows across Python 3.10 and 3.12, so the file-locking behaviour is proven on three real filesystems rather than mocked.
  • Security defaults that fail closed. The server refuses to bind a non-loopback interface without a bearer token, and compares tokens with hmac.compare_digest so comparison is timing-safe.
  • Five supported surfaces. claude.ai web, Cowork, Claude Code, the Chrome extension and Claude Design, packaged both as a Claude Code plugin and as a standalone skill for chat surfaces, both talking to the same server.
  • MIT-licensed and open. The whole thing is public at github.com/Army161/AGORA.

What is not proven yet. A single-file dashboard exists, but it currently renders a demo data layer that mirrors the store schema rather than a live workspace. The remote/HTTPS connector path works locally but has no documented hosted deployment. And a full live test across all five surfaces at once needs real accounts on each — it is on the roadmap below, not behind us.

Why this is defensible

Open source is distribution, not a moat. The argument for defensibility rests on three things, and each of them is currently a hypothesis rather than a demonstrated fact.

It becomes the system of record

Coordination state accretes. Once the tasks, ownership history and handoffs for multi-agent work live in one place, that place is where the answer to "what happened and who did it" lives. Substrates that hold history are replaced slowly.

The event log is the audit trail

The append-only log with a monotonic sequence number is not a feature bolted on for compliance; it is the source of truth the system already needs. Any organisation that has to answer which agent changed what, when, and under whose lease already needs exactly this artifact.

Neutrality is structurally unowned

A coordination layer is only valuable if it works equally well across surfaces and vendors. No single model vendor is incentivised to build that — their incentive is to make coordination work best inside their own product. The neutral position is left open.

The measured version of the neutrality claim: today Agora targets Claude surfaces. Vendor-neutrality is an architectural property of the design — MCP plus plain files, with no vendor-specific state — rather than something proven by a multi-vendor deployment. Treat it as a credible direction, not a completed one.

The obvious counter-argument. A large vendor could ship coordination inside its own product. That would solve the single-vendor case well, and it would probably solve it before anyone else does. It would not solve the case this is built for — a team whose agents do not all come from the same place — and it would make a neutral layer more necessary, not less.

Roadmap

The near-term items are what the repository already implies — seams that exist in the code and need finishing. Anything beyond that is marked speculative.

  1. Hosted remote connector path near-term

    HTTPS serving, bearer-token auth and the loopback refusal already exist, and start scripts for the remote path ship in the repo. What is missing is a documented, repeatable hosted deployment so claude.ai web can join a room without each user standing up their own tunnel.

  2. Dashboard on live workspace data near-term

    The single-file dashboard exists and mirrors the store schema exactly, but it currently renders demo data. Pointing it at a read bridge over the real workspace files turns it from a demonstration into the human cockpit over a running room.

  3. Richer permissions and audit near-term

    Today a single bearer token gates HTTP access, which is the right first control and not a sufficient one. Next are per-agent identity, scoped permissions on tools that mutate shared state, and an export of the event log suitable for review by someone who was not in the room.

  4. Live verification across all five surfaces near-term

    Every surface is wired in configuration, and the engine is tested hard, but a single session with all five surfaces in the same room at once requires real accounts on each. Until that is done and recorded, treat five-surface support as designed rather than demonstrated.

  5. Team hosting and multiple workspaces speculative

    A shared room per team rather than per machine, with membership and retention. Direction only — not designed, not scheduled, and dependent on whether real users ask for it.

  6. Storage backends beyond the folder speculative

    The engine deliberately hides its storage behind a small interface, so a database or object store could replace the folder without changing the tool contract. Whether that is ever worth doing is an open question, not a plan.

  7. Agent surfaces beyond Claude speculative

    Nothing in the engine is Claude-specific, and MCP is the only integration point, so other agent surfaces are architecturally straightforward. Architecturally straightforward is not the same as validated, and no such integration exists today.
